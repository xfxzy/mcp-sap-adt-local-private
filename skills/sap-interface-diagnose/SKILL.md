# SAP 接口诊断 Skill

> 基于真实 SAP 生产环境的接口排障经验，核心原则：**按错误码先分层定位，再逐层深入；先确认"请求到没到 SAP"，再看"到了哪一层"。**

---

## 诊断总流程（5 步走）

```
用户报接口报错
    │
    ▼
第 1 步：分诊 — 按错误码判断大致层级
    │  401 / 403 → 认证/权限层
    │  404       → 路径/服务不存在
    │  500       → 应用层/Dump
    │  timeout   → 性能/网络/死锁
    ▼
第 2 步：定位 — 用 Gateway 错误日志拿第一手证据
    │
    ▼
第 3 步：深挖 — 按方向查 Dump / 源码 / 表 / 配置
    │
    ▼
第 4 步：验证 — 查趋势、查关联、查调用链
    │
    ▼
第 5 步：输出诊断报告
```

---

## 第 1 步：分诊（CRITICAL — 决定方向）

拿到用户描述后，**第一件事是判断错误码类型**，不同错误码查的东西完全不一样。

| 错误码                              | 层级   | 核心问题           | 排查优先级                       |
| ----------------------------------- | ------ | ------------------ | -------------------------------- |
| **401 Unauthorized**          | 认证层 | "你是谁"没通过     | 凭据 → 用户主数据 → 配置       |
| **403 Forbidden**             | 授权层 | "你能不能做"没通过 | 权限对象 → 服务配置 → 用户角色 |
| **404 Not Found**             | 路由层 | "服务/路径不存在"  | URL 拼写 → 服务激活 → ICF 节点 |
| **500 Internal Server Error** | 应用层 | "程序跑崩了"       | Dump → 源码 → 数据             |
| **Timeout / 504**             | 性能层 | "跑太慢/死循环"    | 工作进程 → Dump → SQL 性能     |
| **CORS / 网络级错误**         | 网络层 | "连都连不上"       | 防火墙 → 证书 → 反向代理       |

**关键判断问题（先问自己，再决定下一步）：**

1. **错误码是什么？**（用户没说就主动问，或让用户贴报错截图）
2. **是哪个接口？** OData / REST / RFC / SOAP / IDoc？
3. **是所有用户都报错，还是个别用户？**（全量=配置/服务级问题，个别=用户/权限问题）
4. **之前是好的吗？什么时候开始的？**（突然坏了 = 有变更，一直坏 = 没配好）
5. **报错在 SAP 端能看到吗？**（Gateway 有记录 = 请求到了 SAP；完全没记录 = 卡在更前面）

---

## 第 2 步：定位 — 拿 Gateway 错误日志

> 这步的目的：**确认请求到底到没到 SAP 的应用层，以及到了哪一层。**

### 2.1 调取 Gateway 错误日志

调 `read_http_log`，参数：

- `from` / `to`：用户说的报错时间前后各放宽 5–10 分钟
- `maxResults`：默认 50 条够了，如果时间段大可调到 200

### 2.2 根据日志结果做二分法判断

| 现象                                 | 结论                   | 下一步方向                                                 |
| ------------------------------------ | ---------------------- | ---------------------------------------------------------- |
| 日志里**有**对应时间的错误记录 | ✅ 请求到了 Gateway 层 | 看错误详情，按错误码深入                                   |
| 日志里**完全没有**记录         | ❌ 请求没到 Gateway 层 | 往更前排查：ICF 节点？URL 路径？Client？反向代理？防火墙？ |

### 2.3 读错误详情

如果日志里有记录，调 `read_http_log` 的 `detailUri` 拿完整详情，重点看：

- **Service / Technical Service Name**：哪个 OData 服务
- **Request URI**：完整请求路径
- **HTTP Method**：GET / POST / ...
- **Error Category**：SAP 侧的错误分类（如 `/IWFND/MED000` = 元数据错误）
- **Error Text**：具体报错文本
- **Affected User**：哪个用户
- **Error Resolution**：SAP 给的建议解决方案（如果有）
- **Stack / Context**：完整错误堆栈

## 第 3 步：深挖 — 按错误码方向深入

### 3.1 401 Unauthorized 排查路线

**核心问题：认证失败**

| # | 排查点                   | 怎么查                                         | 工具/方法                       |
| - | ------------------------ | ---------------------------------------------- | ------------------------------- |
| 1 | 用户名密码对不对？       | 让用户确认账号密码；用`sap_system_info` 试连 | 让用户验证 /`sap_system_info` |
| 2 | 用户是否被锁定？         | 查 USR02 表的`UFLAG` 字段（128 = 锁定）      | `read_table` 查 USR02         |
| 3 | 用户是否存在？           | 查 USR02 / USR01                               | `read_table` 查 USR02         |
| 4 | 密码是否过期？           | USR02 的`PWDCHGDATE` + 密码策略              | `read_table` 查 USR02         |
| 5 | Client 是否正确？        | URL 里`sap-client` 参数对不对                | 让用户确认 URL                  |
| 6 | 是不是 SNC / 证书认证？  | 用户配置了 SNC 但服务端没配？                  | 让用户确认认证方式              |
| 7 | 是不是多次输错密码被锁？ | 看错误日志里的失败次数                         | `read_http_log` 详情          |

**401 快速判断口诀：**

> **全用户 401 = 配置/服务问题；单用户 401 = 账号密码问题。**

---

### 3.2 403 Forbidden 排查路线

**核心问题：认证过了，但没权限访问这个服务/资源**

| # | 排查点                     | 怎么查                                 | 工具/方法                           |
| - | -------------------------- | -------------------------------------- | ----------------------------------- |
| 1 | 服务本身是否启用？         | ICF 节点是否激活？                     | 让 Basis 查 SICF                    |
| 2 | 用户有没有服务权限？       | 权限对象`S_SERVICE`、`S_TCODE`     | 让 Basis 查 PFCG                    |
| 3 | OData 服务是否分配了角色？ | Gateway 服务的角色分配                 | 让 Basis 查`/IWFND/MAINT_SERVICE` |
| 4 | 是不是实体级权限？         | 某些 OData 服务有 DPC 扩展里的权限检查 | 读服务实现源码                      |
| 5 | 是不是 CDS 角色/权限？     | S/4HANA 上 CDS DCL 权限                | 查 CDS 角色分配                     |

**403 快速判断口诀：**

> **新接口第一次调就 403 = 配置没做完；以前好的突然 403 = 用户角色变了。**

---

### 3.3 404 Not Found 排查路线

**核心问题：URL 路径不对，或者服务不存在/没激活**

| # | 排查点                       | 怎么查                                               | 工具/方法                                     |
| - | ---------------------------- | ---------------------------------------------------- | --------------------------------------------- |
| 1 | URL 拼写对不对？             | 大小写、拼写、斜杠                                   | 人工核对                                      |
| 2 | 服务名对不对？               | 用正确服务名查                                       | 让用户确认 / Basis 查`/IWFND/MAINT_SERVICE` |
| 3 | 服务是否在这个 Client 激活？ | 有些服务只在特定 Client 激活                         | 让 Basis 查                                   |
| 4 | 实体集名对不对？             | OData URL 里的 EntitySet 名称                        | 读服务元数据`$metadata`                     |
| 5 | ICF 节点是否激活？           | `/sap/opu/odata` 下的节点                          | 让 Basis 查 SICF                              |
| 6 | 是不是路径前缀错了？         | `/sap/opu/odata/sap/` vs `/sap/opu/odata/IWBEP/` | 核对服务路径                                  |

---

### 3.4 500 Internal Server Error 排查路线

**核心问题：SAP 端程序跑崩了（Dump 或未捕获异常）**

1. **先查 Dump**：

   - 调 `list_dumps`，时间窗口和报错时间对齐
   - 如果有对应时间的 Dump，调 `read_dump_detail` 拿详情
   - 然后走 **Dump 诊断 SOP**（调用 `sap-dump-diagnose` skill 的逻辑）
2. **再查 Gateway 错误详情**：

   - `read_http_log` 拿 detail
   - 看 SAP 侧的错误文本和堆栈
   - 定位到具体的 ABAP 类/方法
3. **查源码**：

   - 用 `search_repository_object` 找到出错的类/FM
   - ⚠️ 看返回的 `type`：`FUGR/F`（函数组，URI 不含 `/fmodules/`）不要直接读——先 `get_object_structure` 拿 FM 列表定位
   - 用 `read_source_code` 看出错位置的代码逻辑
4. **查数据**：

   - 报错涉及的业务数据（订单号、物料号等）
   - 用 `read_table` 查对应表，确认数据是否存在、是否正确
5. **查配置**：

   - 是不是配置表缺数据？
   - 是不是某个开关没开？

**500 快速判断口诀：**

> **先查 Dump 再查代码，标准程序先怀疑数据。**

---

### 3.5 Timeout / 超时排查路线

**核心问题：程序跑太久，被超时机制杀掉**

| # | 排查点             | 怎么查                                            | 工具/方法                                          |
| - | ------------------ | ------------------------------------------------- | -------------------------------------------------- |
| 1 | 是哪种超时？       | HTTP 超时(前端) / SAP 工作进程超时 / Gateway 超时 | 看错误信息里的超时来源                             |
| 2 | 有没有产生 Dump？  | 超时通常会有`TIME_OUT` Dump                     | `list_dumps` 查 `TIME_OUT` 类型                |
| 3 | 卡在哪个程序？     | Dump 里的调用栈最上层 / SM50 看进程               | `read_dump_detail`                               |
| 4 | 是不是 SQL 慢？    | 大表查询没走索引？                                | 看程序里的 SELECT，用`read_table` 试一下类似查询 |
| 5 | 是不是死循环？     | 程序里有没有`DO.` / `WHILE.` 没出口？         | `read_source_code` 查循环逻辑                    |
| 6 | 是不是锁等待？     | 等别的进程释放锁                                  | 让 Basis 查 SM12 / SM50                            |
| 7 | 是不是数据量太大？ | 没有分页，一次性取几万条？                        | 看 Dump 里的内表大小                               |

**超时快速判断口诀：**

> **先看有没有 TIME_OUT Dump，有 Dump 看栈顶；没 Dump 看是不是卡在网络/数据库层。**

---

### 3.6 请求没到 Gateway 的排查

如果 Gateway 错误日志里完全没有记录，说明请求在更前面就被拦住了：

| # | 排查点                | 说明                                                                                       |
| - | --------------------- | ------------------------------------------------------------------------------------------ |
| 1 | URL 完全写错了        | 比如域名错了、端口错了、路径前缀错了                                                       |
| 2 | Client 不对           | `sap-client` 写错 → 到了另一个 Client → 该 Client 服务没激活 → 404 而非记录到 Gateway |
| 3 | ICF 节点没激活        | 请求到了 ICF 层但服务节点没激活，直接返回 404/503，不会进 Gateway 日志                     |
| 4 | 反向代理 / WAF 拦截了 | F5、Nginx、Web 应用防火墙在 SAP 前面就拦了                                                 |
| 5 | 防火墙 / 网络不通     | 连不上服务器 → 连接超时 / Connection Refused                                              |
| 6 | HTTPS 证书问题        | 证书过期、域名不匹配 → 客户端直接报错                                                     |

**怎么判断在哪一层？**

- **连不上 / 超时 / Connection Refused** → 网络层/防火墙
- **404 但 Gateway 没记录** → ICF 层或之前
- **401/403 但 Gateway 没记录** → ICF 基本认证或 ICF 权限检查

## 第 4 步：验证 — 交叉确认

定位到初步原因后，**至少再找一个证据交叉验证**，不要一个症状就下结论。

常见的交叉验证方法：

1. **换用户试**：如果怀疑是用户权限问题，换个有权限的用户试一下
2. **换环境试**：DEV 有问题 QAS 有没有？如果 QAS 好的 → DEV 配置问题
3. **查历史**：用 `list_dumps` 或 `read_http_log` 扩大时间范围，看是不是第一次出现
4. **查变更**：最近有没有传过请求？有没有改配置？（可能需要问用户）
5. **查频率**：是每调用必错，还是偶尔错？偶尔错 → 并发/锁/数据问题

## 注意事项

1. **先分层再深入** — 别一上来就查源码，先搞清楚请求到没到 SAP、到了哪一层
2. **Gateway 日志是第一证据** — 所有接口问题第一步都先查 `/IWFND/ERROR_LOG`，它是二分法的分界线
3. **401 别急着说密码错** — 先区分是单用户还是全用户，全用户 401 大概率是配置问题
4. **500 先查 Dump 再查代码** — 和 Dump 诊断 Skill 配合使用
5. **没日志 = 重要信息** — Gateway 没日志本身就是诊断结论，说明请求没到应用层
6. **不确定的让 Basis 查** — SICF、PFCG、SMICM 这些 Basis 事务，不要自己瞎猜
7. **用业务语言输出** — "用户被锁了" ✅，"USR02-UFLAG = 128" ❌
