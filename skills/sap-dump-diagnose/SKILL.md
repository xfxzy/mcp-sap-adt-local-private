# SAP Dump 诊断 Skill

> 基于真实 SAP 生产环境的诊断经验，核心原则：**标准程序的报错先怀疑数据，最后才怀疑代码 Bug。**

---

## 诊断流程（必须按顺序执行）

### 第一步：取证

用户可能指定了 Dump ID，也可能只说"帮我看看最近的 Dump"。

**情况 A：用户给了 Dump ID**
直接调 `read_dump_detail` 拿完整详情。

**情况 B：用户没给 Dump ID**
1. 调 `list_dumps` 获取最近 Dump 列表（默认 50 条，通常够了）
2. 展示摘要给用户确认：
   ```
   最近共 N 条 Dump：
   1. [时间] [错误类型]  [程序]  [用户]
   2. ...
   
   你想诊断哪一个？也可以说"全部诊断"。
   ```
3. 拿到用户选择后，调 `read_dump_detail` 获取完整信息

**情况 C：用户说要诊断哪天的**
用 `from`/`to` 参数指定日期范围，例如 `list_dumps(systemId, from='20260710', to='20260711')`。

---

### 第二步：初始判断（CRITICAL — 这一步决定了后续所有分析方向）

看完 Dump 详情后，**先回答这两个问题**：

#### 问题 1：是标准程序还是自定义程序？

| 程序类型 | 判断依据 | 诊断方向 |
|---|---|---|
| SAP 标准程序 | 程序名不以 `Z` 或 `Y` 开头 | **90% → 数据/配置问题** |
| 自定义程序 | 程序名以 `Z` 或 `Y` 开头 | 可能数据问题，也可能代码 Bug |

#### 问题 2：错误类型是什么？

| 错误类型 | 含义 | 常见根因 |
|---|---|---|
| `DATA_OFFSET_TOO_LARGE` | 字段偏移越界访问 | **几乎总是数据问题**：结构字段宽度改小、动态偏移算错 |
| `UNCAUGHT_EXCEPTION` | 未捕获的异常 | 数据异常导致正常流程抛出异常、缺少 try-catch |
| `COMPUTE_INT_ZERODIVIDE` | 除以零 | 输入数据里有 0 值的字段 |
| `ITAB_DUPLICATE_KEY` | 内表重复键 | 数据源里有重复记录 |
| `MESSAGE_TYPE_X` | 程序主动 DUMP | 需要看具体消息文本 |

**关键原则**：
- `DATA_OFFSET_TOO_LARGE` 在标准程序上出现 → **别急着说"改代码"**。先怀疑字段结构被改过，或动态计算的偏移量参数不对。
- SAP 标准程序经过多年的开发和测试，逻辑层面极少出错。优先排查环境、数据、配置。

---

### 第三步：深挖证据

根据 Dump 信息，**按以下优先级查证据**：

#### 3.1 查源码（理解出错场景）

调 `search_repository_object` 找到出错的程序，然后 `read_source_code` 拉源码。

> **⚠️ 注意对象类型**：搜索结果要看 `type` 字段。如果是 `FUGR/F`（函数组，URI 不含 `/fmodules/`），不要直接 `read_source_code`——会返回整个函数组几千行。应该先用 `get_object_structure` 拿到函数模块列表，再按 Dump 栈里的帧定位到具体 FM 的 include。

> **注意**：标准程序如 `SAPMKCBE` 的源码很复杂。找到 Dump 中提到的 FORM/INCLUDE/方法，重点看那一段。不要试图通读整个程序。

#### 3.2 查配置变更

Dump 里提到的字段名（如 `C_S_DOWNLOAD_DATA`）、结构名（如 `INTO_DOWNLOAD_STRUCTURE`），结合程序模块（如 `EC-EIS-DCM`），判断：
- 这个字段来自哪个配置表/结构？
- 近期有没有人改过这个结构（字段长度、类型）？
- 用户的输入参数和变式（Variant）是什么？

> **注意**：你手头可能没有直接查配置表的能力（没有 `SELECT` 权限），但你可以通过 `read_source_code` 看配置读取逻辑，判断哪些配置会影响偏移计算。

#### 3.3 查调用链

调 `where_used` 看出错程序的引用关系——哪些程序调用了它，它被用在什么业务流程里。

#### 3.4 查频率和趋势

调 `list_dumps` 扩大时间范围（如近 30 天），看看：
- 这个 Dump 是偶发一次还是反复出现？
- 如果反复出现，是每天同一时段吗？（定时任务触发）
- 是同一个用户还是多个用户都遇到？

## 注意事项

1. **不要说"修改 SAP 标准程序"** — 这会让开发团队反感，也不可行。优先说"查配置"、"限制输入"、"打补丁"。
2. **不要跳过第二步直接给结论** — 先判断程序类型和错误类型，选对分析方向。
3. **不确定的就说"需要确认"** — 如实列出待确认的信息，比强行给结论更专业。
4. **用业务语言** — 用户可能是业务顾问，不是 ABAP 开发。用"字段长度不够"而不是"CX_SY_RANGE_OUT_OF_BOUNDS 在方法 XYZ 中未被捕获"。
5. **用户操作上下文永远是最重要的证据** — 问清楚谁在什么时候做了什么、用的什么参数，往往能直接定位问题。
